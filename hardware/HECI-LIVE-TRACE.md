# Живий HECI-трейс: `fw-version` через легітимного власника (`mei_me`), без BAR-доступу

**Місія 3C (2026-09-03).** Перший `LIVE-CONFIRMED` зв'язок між
нормальною kernel-mediated MEI-транзакцією (`fw-version`) і реальними
значеннями регістрів `H_CSR`/`ME_CSR_HA` — отримано через два вже
наявні tracepoints ядра (`mei_reg_read`, `mei_reg_write`,
`hardware/HECI-TRANSPORT-MODEL.md`), без жодного доступу до BAR0,
без нового коду, без нових команд у ME. Точна процедура —
`probe/heci-trace-capture.sh` (коміт `0590f0c`), сирий вивід —
`probe/heci-fw-version.trace` (153 рядки, доданий поряд).

## Дві реально атрибутовані ділянки (за PID `mei-observer`)

Файл трейсу містить багато рядків від `irq/140-mei_me` та інших
процесів (`kworker`, `konsole`, `sudo`) — це реальний, живий трафік
на спільному каналі, **не вигаданий і не домальований**, але й не
весь однозначно атрибутований саме нашій транзакції (див. розділ
"Чесна межа" нижче). Лише рядки з тегом `mei-observer-11150` точно
й однозначно належать нашому запиту — по них і побудовано таблицю.

### Ділянка 1 — `IOCTL_MEI_CONNECT_CLIENT` (HBM connect, рядки 69–73)

| Час (offset, мс) | RAW event | Інтерпретація |
|---|---|---|
| +0.000 | `H_CSR read = 0x80020229` | `CBD=128 CBWP=2 CBRP=2 RST=0 RDY=1 IG=0 IS=0 IE=1` |
| +0.000 | `H_CSR read = 0x80020229` | те саме значення (повторне читання) |
| +0.002 | `H_CSR read = 0x80040229` | `CBWP=2→4` — драйвер уже записав 2 DWORD (заголовок HBM-запиту + сам `hbm_client_connect_request`) до цього моменту |
| +0.003 | `H_CSR write = 0x8004022d` | `IG=0→1` — сигнал "дані готові" |
| +0.008 | `ME_CSR_HA read = 0x8005050b` | `CBWP=CBRP=5, RDY=1, IS=1` — ME вже відповіла (біт `IS` встановлений) |

### Ділянка 2 — `write()` самого MKHI fw-version запиту (рядки 121–124)

| Час (offset, мс) | RAW event | Інтерпретація |
|---|---|---|
| +0.000 | `H_CSR read = 0x80070729` | `CBD=128 CBWP=7 CBRP=7 RST=0 RDY=1 IG=0 IS=0 IE=1` |
| +0.002 | `H_CSR read = 0x80090729` | `CBWP=7→9` — знову +2 DWORD: `mei_msg_hdr` (4 байти = 1 DWORD) + наш payload `ff020000` (4 байти = 1 DWORD), точно збігається з реальним розміром запиту |
| +0.003 | `H_CSR write = 0x8009072d` | `IG=0→1` |
| +0.007 | `ME_CSR_HA read = 0x800d0d0b` | `CBWP=CBRP=13, RDY=1, IS=1` |

## Delta — те, що реально змінилось у `H_CSR write` (не повний регістр)

```text
before = 0x80090729
after  = 0x8009072d
XOR    = 0x00000004   ->  лише біт H_IG (0x4)
```

**Це пряме, живе підтвердження точного твердження з Місії 2**
(`mei_hcsr_set_hig()` встановлює лише біт `H_IG`, нічого іншого) —
не логічний висновок із коду, а реально виміряна дельта на фізичному
залізі. `CBD` (128, буферна глибина), `RDY` (1) і `RST` (0) лишились
незмінними в обох випадках запису — узгоджено з тим, що це рутинна
передача даних, не reset і не renegotiation.

## Що НЕ домальовано, сказано чесно

- **`H_CB_WW` не трасується цим механізмом** (підтверджено раніше —
  `mei_reg_read`/`mei_reg_write` викликаються лише для `H_CSR`,
  `ME_CSR_HA`, `H_D0I3C`, `H_HPG_CSR`, `ME_TRC`, не для `H_CB_WW`
  напряму) — тому статус:
  ```text
  SOURCE-CONFIRMED: Linux пише H_CB_WW (mei_me_hbuf_write(), Місія 2)
  LIVE-CONFIRMED:   H_CSR transition (CBWP +2, IG 0->1) спостережено
  UNKNOWN:          точні окремі DWORD-и H_CB_WW в цьому конкретному запуску
  ```
- **Решта ~140 рядків трейсу (не позначені `mei-observer`) —
  реальний, живий трафік, не вигадка, але й не атрибутований тут
  конкретній причині.** Найімовірніші джерела (не підтверджено):
  фонова активність інших зв'язаних клієнтів (`mei_hdcp`, `mei_pxp`),
  чи power-gating (`H_HPG_CSR`, бачили `H_D0I3C` активність від
  `kworker` ще до старту нашого запиту, у самому idle-baseline —
  підтверджує, що канал ніколи не був повністю тихим навіть у стані
  спокою). Свідомо не декодовано й не приписано без підтвердження —
  залишено `UNKNOWN`, а не заповнено здогадкою.

## Контрольний приклад — сама MKHI-відповідь

```text
mei-observer:
REQUEST  ff020000
RESPONSE ff820000...3425
```

Той самий `11.8.50.3425`, що й у всіх попередніх незалежних методах
цієї сесії — тепер із реальним, задокументованим ланцюжком змін
регістрів між запитом і відповіддю, не лише кінцевим результатом.

## Критерій завершення Місії 3C

Отримано перший `LIVE-CONFIRMED` зв'язок між нормальною
kernel-mediated MEI-транзакцією `fw-version` і фактичними значеннями
`H_CSR`/`ME_CSR_HA`, без прямого доступу до BAR і без зміни поведінки
драйвера. Зупинено тут — без переходу до прямого MMIO.
