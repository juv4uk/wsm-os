# entropy-source-probe: реальні, емпіричні результати

За прямою інструкцією власника припинити обговорення й почати
дослідження того, що "порожня система" на реальному залізі може
дізнатись про реальність. Запуск 2026-09-02, QEMU/OVMF/TCG
(`-cpu Skylake-Client-v1,+rdrand,+rdseed`).

## Реальний зафіксований вивід

```text
CPUID reports RDRAND=1 RDSEED=1
Samples requested: 256
Successful reads:  256
Total bits set across successful 64-bit samples: 8177 of 16384 (expect ~50% if genuinely uniform)
Retries-before-success: sum=0 mean_x1000=0 max=0
```

## Чесна інтерпретація (SINGULAR EXTERNAL підтвердження PLURAL INTERNAL-даних проби)

- **Баланс бітів: 49.9% одиниць.** Близько до очікуваних 50% для
  рівномірно випадкових даних. Це саме по собі не розрізняє реальну
  апаратну ентропію від добре засіяного програмного PRNG — обидва
  пройшли б цей тест.
- **Нуль повторних спроб на 256 викликах — реальна знахідка.** На
  справжньому кремнії Intel RDSEED документовано іноді повертає
  провал (CF=0), бо кондиціонер ентропії на кристалі не накопичив
  достатньо свіжої ентропії з часу останнього забору — це очікувана,
  нормальна поведінка, не помилка. Отримання **нуля** провалів на 256
  викликах саме по собі є доказом: сильно натякає, що емуляція RDSEED
  у QEMU/TCG взагалі не моделює реальну апаратну поведінку
  виснаження-ентропії/повторних спроб — найімовірніше, вона бере дані
  з власного випадкового джерела ОС хоста (зрештою засіяного реальною
  апаратною ентропією десь на цьому хості WSL2, але через ОС, не
  вірна емуляція власного DRNG гостьового CPU під навантаженням) і
  завжди повідомляє успіх.
- **Наслідок для оригінального питання**: ідея "поведінка
  повторних-спроб-перед-успіхом схожа на геометричний/пуассонівський
  процес" з `wsm/research/hardware-native-constants.md`
  **неможлива для перевірки в цьому середовищі QEMU/TCG** — тут нема
  поведінки повторних спроб, яку можна виміряти. Це реальна,
  структурна межа поточного налаштування лабораторії, не глухий кут
  для самої ідеї: знадобилось би або виконання на реальному фізичному
  залізі (окрема, авторизована власником майбутня робота, та сама
  межа, вже заявлена в `docs/QEMU-SETUP.md`), або конфігурація
  CPU/акселератора QEMU, що реально моделює виснаження ентропії, чого
  тут не пробувалось.

## Що ця проба реально демонструє, незалежно від питання про ентропію

- `RDRAND`/`RDSEED` — реальні, присутні, викличні інструкції в цьому
  лабораторному середовищі (`CPUID` підтверджує обидва біти),
  збігається з власними задокументованими ISA-функціями реального
  CPU власника (`OWNER-HARDWARE-PROFILE.md`).
- Сама проба — робочий, повторно використовний інструмент: вона
  збирає реальні зразки, обчислює реальну статистику (баланс бітів,
  кількість повторних спроб), і друкує сирі дані для зовнішньої
  перевірки замість того, щоб стверджувати власні висновки — точно те
  розділення `PLURAL INTERNAL` (породження кандидатів) /
  `SINGULAR EXTERNAL` (підтвердження, зроблене тут, стороною, іншою
  за саму пробу), яке вимагає `wsm/research/the-observer-gap.md`.
- Також зафіксовано дельту таймінгу `RDTSC` за фіксованим циклом
  очікування (`0x7624D84` циклів), навмисно лишену неінтерпретованою
  в самій пробі — друга реальна апаратно-суміжна величина, доступна
  для майбутнього аналізу, тут ще не проаналізована.

## Чесний статус

Це один запуск, на одній віртуальній машині, під одним програмним
емулятором. За власною драбиною сили доказів цього проєкту (`local
run < clean CI run < reproducible CI test < independent external
reproduction`), це стоїть на найнижчому щаблі — реальний, емпірично
підтверджений локальний результат, ще не відтворений, ще не запущений
на фізичному залізі. Конкретна, корисна знахідка (RDSEED під TCG не
моделює реальне виснаження ентропії) тверда на цьому щаблі; будь-що
про власну статистику ентропії *реального* CPU лишається невиміряним.
